# Решения и допущения

## Где ТЗ допускало разные толкования

1. **Роли хранятся в таблице `profiles`.** Профиль создаётся триггером при добавлении пользователя в Supabase Auth.
   Роль берётся из `app_metadata`, который может задать только администратор, а не из `user_metadata`, который пользователь меняет сам.
   По умолчанию роль «Исполнитель»: так безопаснее. Сменить роль можно только через SQL или Studio.
2. **Любой постановщик принимает и возвращает любую задачу**, а не только автор. В ТЗ сказано «постановщик», без уточнения.
3. **Исполнителем назначается только пользователь с ролью «Исполнитель».** Проверка в базе.
4. **Принятую задачу нельзя редактировать** (название, описание, объект, исполнитель). Иначе после приёмки можно «подменить», что было принято.
   Удалить её постановщик по-прежнему может.
5. **Редактировать задачу в других статусах можно, включая смену исполнителя.** Статус при этом не сбрасывается:
   новый исполнитель продолжает с того же места. Смена исполнителя в историю не пишется, потому что история по ТЗ про статусы.
6. **Удаление задачи удаляет и её историю.** Удалять задачи постановщику разрешено по ТЗ, а история без задачи не имеет смысла.
   Через API отдельно от задачи историю удалить нельзя. Удаление объекта удаляет его задачи; интерфейс предупреждает об этом.
7. **Исполнитель видит имена постановщиков** (авторы задач и записи истории), но **не видит других исполнителей**.
8. **«Мои задачи»:** у исполнителя это его задачи, у постановщика тот же экран называется «Все задачи». Есть фильтры по статусу и поиск.
9. **Ошибки «чужая задача» и «задачи не существует» выглядят одинаково**, чтобы исполнитель не мог перебором узнать, какие задачи есть.

## Как устроена защита (кратко, для технического созвона)

- RLS включён на всех таблицах. У `anon` нет ни прав, ни политик. Хелперы `is_manager()` и `is_executor()` сделаны `security definer`
  в непубликуемой схеме `private`.
- Второй рубеж: привилегии по колонкам. На `tasks` `authenticated` может писать только `object_id, title, description, assignee_id`.
  Колонки `status`, `author_id` и `created_at` через API не задать.
- **Статус меняется только функцией `change_task_status()`.** Она блокирует строку (`for update`), сверяет переход
  с таблицей `private.status_transitions`, проверяет, кто действует и есть ли обязательный комментарий, и пишет историю.
  Триггер на `tasks` запрещает менять `status` любым другим путём, даже из SQL-редактора, чтобы история не разъехалась с задачей.
- **История:** INSERT/UPDATE/DELETE не выданы ни одной API-роли. Записи пишут только триггер создания и функция смены статуса.
  UPDATE запрещён триггером даже суперпользователю.
- Таблица переходов `private.status_transitions` — единственный источник правды. Интерфейс держит её зеркало (`src/lib/status.ts`)
  только для того, чтобы показывать нужные кнопки.
- Регистрация выключена (`enable_signup = false` в `config.toml` и в настройках облачного проекта).
- В браузер попадает только publishable-ключ. Секретный нужен лишь локальному скрипту `seed` и лежит в `.env.seed.local` (в `.gitignore`).
- `npm run security-check`: 36 автоматических проверок в обход интерфейса, все проходят.

## Что сознательно не делал или не успел

- **Управление пользователями из интерфейса.** Пользователей заводит администратор в Supabase. Для этого нужен серверный код
  с секретным ключом (Edge Function), а в ТЗ сказано «создать вручную».
- **Сброс и смена пароля, приглашения по почте.** Не входят в ТЗ.
- **Realtime-обновления.** Данные обновляются при переходах между экранами и после действий, но не «вживую» от других пользователей.
- **Пагинация.** Для объёмов CRM одной компании списки грузятся целиком. При тысячах задач понадобится серверная пагинация.
- **Аудит изменений полей задачи** (кто поменял описание или исполнителя). По ТЗ история нужна только для статусов.
- **Сроки, вложения и фото с объекта** — очевидные следующие шаги для стройки, но их нет в ТЗ.
- **E2E-тесты интерфейса.** Логика безопасности покрыта `security-check`, интерфейс проверял вручную и скриншотами.
